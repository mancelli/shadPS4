# Почему старая сборка BBFork от 05.11.2025 может давать больше FPS, чем 12739d2

> **Статус на 2026-10-17.** Анализ кода, FPS никто не замерял. Сравнивались BBFork
> `a8d954e` (05.11.2025, «Reducing stutters with Readbacks») и релиз форка `12739d2`
> (2026-10-14). Что изменилось после отчёта:
> - пять режимов Readback Speed заменены переключателем On/Off, подмены для UFC 4 больше нет
>   (cdfb6fa). Пункт 1 теперь проверяется в любой игре: Off = прежний Disable;
> - пункты 2–5 (синхронная выгрузка изображений, flush при записи CPU даже с Off, сборщик
>   мусора, depth-as-color) не менялись и остаются кандидатами.
>
> Номера строк — для кода `12739d2`. Полные находки с проверками:
> [bbfork-2025-11-05-fps-findings.json](bbfork-2025-11-05-fps-findings.json).

## 1. Коротко: вероятные причины (по убыванию)

1. **Readback по умолчанию Low вместо Disable.** Уверенность высокая. Источник: наш форк (b7285a7, ef844c9).
   - В OLD по умолчанию был Disable (config.cpp:173).
   - В NEW на новой установке и после «Restore Defaults» выставляется Low (config.cpp:1958-1970).
   - Для UFC 4 (CUSA14204/14209) значения Disable и Unsafe в релизе всегда превращаются в Low (config.cpp:1237-1261).
   - Каждое чтение CPU из памяти, которую записал GPU, в режиме Low ведёт к fault и `scheduler.Finish()` (buffer_cache.cpp:104-168).
   - Условия: UFC 4 всегда, любая GPU; другие игры только на новой установке. Сильнее всего на iGPU и Arc.
   - Оговорка: в OLD часть FPS в UFC 4 получалась за счёт того, что головы бойцов отрисовывались неправильно.
2. **Синхронная выгрузка изображений.** Уверенность средняя. Источник: апстрим/Shadlix.
   - В OLD изображения выгружались асинхронно, в отдельном потоке.
   - В NEW `ProcessDownloadImages` вызывает `DownloadImageMemory(id, true)`, то есть `Finish()` на каждое изображение (texture_cache.cpp:102-140). Это происходит на каждом EOP/EOS/WriteData (liverpool.cpp:770, 791, 846, …).
   - Источники таких выгрузок: 1×1 render target (vk_rasterizer.cpp:1346-1356, UFC не в списке исключений) и, из нашего форка, линейные storage-изображения от 64×64 (texture_cache.cpp:87-98, 966-976).
   - Если UFC рисует в 1×1 каждый кадр, потеря может превышать 15%. Из кода это не подтверждено.
3. **Depth-as-color для теней UFC 3/4.** Уверенность средняя/низкая. Источник: наш форк (7225129).
   - При каждом bind теневой карты запускается compute-конвертация и render pass разрывается (vk_rasterizer.cpp:83-212, 1196-1209). Проверки «уже сконвертировано» нет.
   - Автор коммита сообщал, что FPS не изменился, но мерил только на UFC 3 и Arc.
4. **Режим Disable в NEW больше не избавляет от readback.** Уверенность средняя (в основном стоттер). Источник: апстрим.
   - Когда CPU пишет в страницу, которую записал GPU, NEW всё равно скачивает её и ждёт GPU (memory_tracker.h:91-105). В OLD при Disable это пропускалось.
   - Настройкой это не отключается.
5. **Сборщик мусора текстур фактически не работает.** Уверенность средняя. Источник: апстрим.
   - `RunGarbageCollector` нигде не вызывается (texture_cache.cpp:1296). В OLD он запускался на каждый submit.
   - Последствие: FPS падает к концу длинной сессии на картах с 6–8 ГБ (GTX 1660, Arc A3xx/A5xx, 4060 Ti 8GB).
6. **MAD/MAC разбиты на FMul+FAdd с NoContraction.** Уверенность низкая/средняя, независимой проверки не было. Источник: апстрим.
   - vector_alu.cpp:737-749, 1390-1395. Касается всех GPU и сцен, где упираемся в ALU.
7. **Только для Intel: несколько мелких изменений, вместе заметнее.** Уверенность низкая. Источник: наш форк (8034718).
   - Принудительный SIMD32 (vk_instance.h:252-263).
   - Барьеры workgroup для LDS (vk_pipeline_cache.cpp:371-373).
   - Subgroup-барьеры, NaN guard, «плоские» workgroup.
8. **Конфиг, перенесённый из старой версии.** Уверенность средняя.
   - Режим Fast в NEW работает как Low (region_manager.h:102-103, апстрим).
   - Если в конфиге нет ключа `pipelineCacheEnable`, кэш шейдеров выключен.
   - Если кэш создан другой сборкой, он молча игнорируется и больше не пишется (vk_pipeline_serialization.cpp:337-351). Наш форк поменял раскладку `Shader::Profile`, поэтому это вероятно.
   - Синхронное сохранение VkPipelineCache каждые 50 новых pipeline даёт рывки (vk_pipeline_cache.cpp:464, 494; наш форк e669792).

## 2. Что в NEW быстрее

- Дисковый кэш шейдеров с прогревом (WarmUp). В OLD его не было совсем. Меньше стоттера со второго запуска.
- Ограничитель FPS: с лимитом N в UFC теперь будет N FPS, а в OLD было N/2 (driver.cpp:392-422, наш 15b0af1). Поэтому OLD с лимитом 120 надо сравнивать с NEW с лимитом 60.
- Загрузки идут через отдельный command buffer, staging-буферы не ждут GPU.
- Когда readback включён, он дешевле: одно окно 512 КБ вместо отдельного Finish на каждые 4 КБ.
- Барьеры собираются пакетами; PFP_SYNC_ME больше не разрывает render pass.
- Убраны bounds-check для всех обращений к LDS. Host-шейдеры скомпилированы заранее.
- Сообщения лога, которые всё равно отфильтруются, больше не форматируются.

## 3. A/B-тесты без новой сборки (по приоритету)

1. **UFC 3 / другие игры:** Readback Speed = Disable (`readbackSpeedMode=0`). Если FPS вырос, причина в п. 1.
   **UFC 4:** на 12739d2 переключить нельзя. На бете cdfb6fa поставить Off: если FPS вернулся, причина в readback (головы при этом сломаются).
2. **`SHADPS4_DEPTH_AS_COLOR=0`.** На Intel/AMD тени станут неправильными, но так проверяется п. 3.
3. **`SHADPS4_LINEAR_STORAGE_READBACK=0`.** Проверяет часть п. 2.
4. **Кэш шейдеров.**
   - Проверить, что `pipelineCacheEnable=true`.
   - Поискать в логе строку «Pipeline cache isn't compatible». Если есть, удалить `user/cache/<serial>`.
   - Важно: любые env-переменные `SHADPS4_*` переключают кэш на отдельную папку. Поэтому каждый тест надо запускать дважды и мерить на втором запуске.
5. **Одинаковые настройки FPS:** сравнивать при выключенном лимитере и vblank 60.
6. **Сессия 30+ минут.** Если FPS постепенно падает, это GC (п. 5).
7. **Intel:** попробовать `SHADPS4_LDS_ORDER=0`, `SHADPS4_NAN_GUARD=0`, `SHADPS4_FLATTEN_WG=0`.
8. **Логи:** `logType="async"` или `logEnabled=false`.
9. **Меню Create Fighter:** `SHADPS4_FLUSH_CPU_WRITE=0`, `SHADPS4_BC_MODE=2`.

Попросить у игрока лог. В нём видны GPU, строка «Subgroup size range …», переопределение readback и строка «Vulkan pipeline cache: loaded N KB».

## 4. Что мы можем поменять в коде

| Изменение | Риск |
|---|---|
| Передать `sync=false` в `ProcessDownloadImages` (асинхронный путь уже есть, texture_cache.cpp:141-148) | средний: данные 1×1 будут запаздывать на кадр |
| Исключить UFC из `Schedule1x1Readback` / `ShouldDisableSync` | средний: возможны визуальные регрессии |
| Depth-as-color: конвертировать только если depth изменился с прошлого раза | низкий |
| Readback для UFC 4 только для нужных диапазонов (head compute), а не глобальный Low | высокая трудоёмкость, большой выигрыш |
| Вернуть для Disable пропуск flush в `InvalidateRegion` | средний: риск неверных данных |
| Снова вызывать `RunGarbageCollector` (и чинить `gc_tick`) | средний: возможны рывки при вытеснении |
| Сохранять VkPipelineCache в IO-потоке или только при выходе | низкий |
| Новые поля `Profile` добавлять в конец и поднимать версию кэша | низкий |
| Переключатели для Intel SIMD32 / `needs_lds_barriers` | низкий |
| Опция «FMA для MAD» | средний: расхождения точности |

## 5. Что неизвестно и что опровергнуто

- Неизвестно, какая игра и какая GPU у игрока. Из кода не видно, рисует ли UFC в 1×1 каждый кадр, использует ли clip distances (это важно для NVIDIA) и пишет ли линейные storage-изображения в бою. Ничего из этого не измерялось.
- Если игрок использовал собственный конфиг OLD (vblank, лимитер, Fast), сравнение некорректно.
- Опровергнуто или не влияет на FPS:
  - Тулчейн сборки идентичен.
  - «Thundering herd» в семафорах: без конкуренции NEW даже быстрее.
  - HR-таймеры.
  - Масштаб GPU-таймстампов: в UFC нет динамического разрешения.
  - ZPASS/predication: для UFC не доказано.
  - Флаги cpuCoreMode, app0 bandwidth, memoryCompression ничего не делают.
  - Collect Debug Logs без включения ничего не стоит.
  - Глубина flip-очереди.
  - Таблица страниц +512 МБ влияет только на нехватку RAM.
  - OutputDebugStringW в логах — малый эффект, только при спаме в лог.
